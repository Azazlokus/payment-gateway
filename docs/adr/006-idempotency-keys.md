# ADR-006: Idempotency Keys для создания платежей и возвратов

## Status
Accepted

## Context

Сетевые сбои — норма. Клиент отправил `POST /payments`, сервер создал платёж и начал ответ, но соединение разорвалось. Клиент не знает: платёж создан или нет? При повторе — создастся второй платёж.

Для платёжных систем двойное списание критично.

Аналогичная проблема с возвратами: повторный запрос возврата = двойной возврат.

## Decision

Клиент передаёт заголовок `Idempotency-Key: <uuid>` с каждым мутирующим запросом. Сервер гарантирует что операция с тем же ключом выполнится только один раз.

Реализация через `IdempotencyMiddleware` в CommandBus pipeline:

```
POST /payments  [Idempotency-Key: 550e8400-...]
    → CommandBus
        → ValidateCommand
        → IdempotencyCheck          ← проверяем ключ в payments таблице
            если найден → вернуть существующий результат (не создавать)
            если нет    → выполнить команду, сохранить ключ
        → Handle
```

Правила:
- Если `Idempotency-Key` не передан — генерируется автоматически (запрос не идемпотентен, но не ломается)
- Ключ хранится в колонке `idempotency_key` таблицы `payments`
- Очистка устаревших ключей: команда `payments:prune-idempotency-keys` (ежедневно в 02:00)
- При повторном запросе с тем же ключом возвращается `409 IdempotencyViolationException` если параметры запроса отличаются

## Consequences

**Плюсы:**
- Клиент безопасно ретраит запросы при сетевых ошибках
- Двойное создание платежа / двойной возврат исключены на уровне протокола
- Совместимо с YooKassa API (они тоже используют idempotency key)

**Минусы:**
- Клиент обязан генерировать и хранить UUID — дополнительная ответственность
- Таблица `payments` содержит `idempotency_key` — нужна периодическая очистка
- Не защищает от concurrent запросов (race condition на уровне транзакций БД)
