# ADR-001: Clean Architecture + Domain-Driven Design

## Status
Accepted

## Context

Платёжный шлюз интегрирует несколько внешних провайдеров (YooKassa, Robokassa, CloudPayments, СБП, Альфа-Банк) и крипто-блокчейны (TON, TRON, Bitcoin). Каждый провайдер имеет свой протокол вебхуков, формат данных и правила верификации.

Без чёткой архитектуры:
- Бизнес-логика смешивается с HTTP-слоем и деталями провайдеров
- Добавление нового провайдера затрагивает несколько несвязанных мест
- Тестирование требует поднятия внешних сервисов
- Домен (правила возврата, статусные переходы) невозможно протестировать изолированно

## Decision

Используем **Clean Architecture** с разделением на слои и **DDD** для моделирования платёжного домена.

Структура каждого bounded context:

```
Domain/          — чистая бизнес-логика, zero dependencies на фреймворк
Application/     — use cases, CommandBus, DTO
Infrastructure/  — адаптеры к внешним системам (провайдеры, БД, Redis)
Presentation/    — HTTP-слой (контроллеры, реквесты, ресурсы)
```

Ключевые принципы:
- **Dependency Rule**: зависимости направлены внутрь. Domain не знает о Laravel, Eloquent или провайдерах
- **Агрегаты** (`Payment`, `Dispute`, `CryptoDeposit`) — единственные точки изменения состояния
- **Доменные события** фиксируют что произошло, не как
- **Провайдеры** реализуют `PaymentProviderInterface` — домен не знает о конкретных SDK
- **Bounded contexts**: `Payments` и `CryptoPayments` независимы, общаются через ACL

## Consequences

**Плюсы:**
- Бизнес-правила (статусные переходы, ограничения возврата) тестируются unit-тестами без БД и HTTP
- Новый провайдер = новый класс реализующий интерфейс, без изменения домена
- `Payment` — `final class`, намеренно запечатан от наследования
- Чёткие границы упрощают онбординг: разработчик понимает где искать логику

**Минусы:**
- Больше файлов и классов, чем в типичном Laravel CRUD
- Overhead для простых операций (mapping DTO → агрегат → модель)
- Требует дисциплины: легко нарушить слои добавив `use Illuminate\...` в Domain
