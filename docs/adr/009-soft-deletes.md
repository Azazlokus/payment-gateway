# ADR-009: Soft Deletes для таблицы payments

## Status
Accepted

## Context

Платежи иногда нужно «удалять» из UI (мусорные тестовые записи, дубли), но физическое удаление из таблицы `payments` недопустимо по нескольким причинам:

1. **Финансовый аудит**: регуляторы (ФНС, ЦБ) требуют хранить историю финансовых операций. Удалённая запись = дыра в аудите.
2. **Idempotency keys**: если запись удалена физически, повторный запрос с тем же `idempotency_key` создаст новый платёж вместо возврата существующего.
3. **Внешние ссылки**: `payment_events`, `disputes`, `crypto_refund_requests` ссылаются на payments через FK. Физическое удаление требует каскадного удаления или нарушает ссылочную целостность.
4. **Восстановление**: ошибочно «удалённый» платёж можно восстановить через `restore()`.

## Decision

Используем **soft deletes** через `deleted_at` timestamp и трейт `SoftDeletes` в Eloquent.

```php
// PaymentModel
use SoftDeletes;

// Обычный запрос — мягко удалённые платежи не видны
Payment::all(); // WHERE deleted_at IS NULL

// Включая удалённые
Payment::withTrashed()->find($id);

// Только удалённые
Payment::onlyTrashed()->get();

// Восстановление
Payment::withTrashed()->find($id)->restore();
```

Физическое удаление (`forceDelete()`) запрещено на уровне code review — только через явный maintenance-скрипт с подтверждением.

## Consequences

**Плюсы:**
- Аудит-трейл сохраняется; FK-целостность не нарушается
- Восстановление одной строкой кода
- Idempotency keys работают корректно для восстановленных записей
- Laravel реализует через `WHERE deleted_at IS NULL` — прозрачно для всех запросов

**Минусы:**
- Таблица растёт со временем — нужна политика архивирования для старых soft-deleted записей
- Индексы должны включать `deleted_at`: составные индексы вида `(status, deleted_at)` вместо `(status)`, чтобы не делать full scan
- Разработчики должны помнить про `withTrashed()` в admin-инструментах и отчётах
