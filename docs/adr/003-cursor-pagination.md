# ADR-003: Cursor-based пагинация вместо offset

## Status
Accepted

## Context

Список платежей (`GET /api/v1/payments`) использовал стандартную offset-пагинацию:

```sql
SELECT * FROM payments ORDER BY created_at DESC LIMIT 20 OFFSET 10000
```

Проблемы offset при росте таблицы:
1. **Производительность**: база читает и пропускает N строк перед возвратом результата. `OFFSET 10000` = 10020 строк прочитано, 20 отдано
2. **Нестабильность**: если между запросами страниц добавились новые записи — строки смещаются и клиент пропустит записи или увидит дубли
3. **Нет индекса**: PostgreSQL не может использовать индекс для пропуска строк через OFFSET

Для платёжного шлюза с потенциально миллионами транзакций это критично.

## Decision

Используем **cursor-based пагинацию** через Laravel `cursorPaginate()`.

Механизм: вместо номера страницы клиент передаёт курсор — opaque base64 строку, кодирующую значения последней записи. Запрос становится:

```sql
SELECT * FROM payments
WHERE (created_at, id) < (cursor_created_at, cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 20
```

Двойная сортировка `created_at + id` обязательна: два платежа могут иметь одинаковый `created_at`, тогда курсор по одному полю неуникален.

Изменение API:
```json
// Было
{ "data": [...], "total": 5420, "current_page": 3, "last_page": 271 }

// Стало
{ "data": [...], "per_page": 20, "next_cursor": "eyJpZCI6...", "prev_cursor": null }
```

## Consequences

**Плюсы:**
- O(log n) независимо от глубины страницы — PostgreSQL использует индекс
- Стабильные результаты: новые записи не сдвигают страницы
- Laravel реализует прозрачно через `cursorPaginate()`

**Минусы:**
- Нельзя прыгнуть на произвольную страницу (например, "перейти на страницу 50")
- Нет `total` — нельзя показать "запись X из Y"
- Курсор непрозрачен для клиента — нельзя сконструировать вручную
- Если клиенты использовали `?page=N` в URL — breaking change

Для платёжного дашборда (последовательная навигация) эти ограничения приемлемы.
