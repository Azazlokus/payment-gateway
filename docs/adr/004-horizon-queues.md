# ADR-004: Laravel Horizon для обработки вебхуков

## Status
Accepted

## Context

Вебхуки от провайдеров требуют немедленного ответа (провайдер ждёт 200 OK, иначе ретраит). При этом обработка вебхука включает:
- Верификацию подписи / IP
- Запрос к БД (поиск платежа)
- Обновление агрегата
- Запись доменных событий
- Отправку уведомлений клиенту

Всё это синхронно в HTTP-запросе = медленно и ненадёжно.

Альтернативы для очередей:
- **database driver** — простой, без зависимостей, но polling каждую секунду нагружает БД
- **Redis + Horizon** — in-memory, мгновенная доставка, веб-интерфейс мониторинга
- **RabbitMQ / SQS** — enterprise решения, избыточны для одного сервиса

## Decision

Используем **Laravel Horizon** поверх Redis.

Архитектура обработки вебхука:
```
POST /webhook/{provider}
    → верификация (IP / HMAC / X-Api-Key)     # синхронно, < 1ms
    → ProcessWebhookJob::dispatch()            # кладём в Redis очередь
    ← 200 OK                                  # немедленно

ProcessWebhookJob (async, Horizon)
    → парсинг payload
    → обновление Payment агрегата
    → сохранение в БД
    → audit log + метрики
```

Настройки надёжности:
- **5 попыток** с экспоненциальным backoff: 10s → 30s → 60s → 120s → 300s
- После 5 неудач → `failed_jobs`, Slack алерт (метрика `failed_jobs_count`)
- Приоритетные очереди: `payments-critical` (2-10 воркеров) > `payments` > `default`
- Graceful shutdown: `horizon:terminate` ждёт завершения текущих задач

## Consequences

**Плюсы:**
- Провайдер получает 200 OK за < 5ms — минимум повторных попыток
- Horizon UI показывает throughput, pending jobs, failed jobs в реальном времени
- Redis in-memory — latency очереди < 1ms
- Автоматическое масштабирование воркеров по нагрузке

**Минусы:**
- Зависимость от Redis — если Redis упал, вебхуки не обрабатываются
- Асинхронность: статус платежа обновляется с небольшой задержкой
- Horizon требует отдельного процесса (отдельный Docker контейнер `prod-worker`)
